Think Fast: Local Decision Models

Build an engine that answers typed questions with honest probabilities, in milliseconds, on your own hardware. Then use it to clean a messy dataset: automate the calls it is sure about and send the rest to a person.

What a decision engine does

It reads the input once and returns a probability for every answer you defined. It writes no text.

One endpoint: POST /v1/systemone, the same format Kev and other open decision models already speak. Full contract in docs/decision-api.md.

Five levels

Each level is a demo on its own. Go as far as you can.

  1. Serve itA local engine on the decision API that passes the starter repo's evaluation runner.
  2. Make it honestCalibrate: when it says 90%, it should be right 9 times in 10. Measure Brier and calibration error, then fix them (temperature scaling is a good start).
  3. Make it fastSeveral questions per request, fast at p95. Read the input once and share it across questions; cache, batch, quantise.
  4. Make it yoursFine-tune or distil for data work, without losing the task types you have never seen.
  5. Put it to workA tool on the messy product catalogue: automate above a threshold, send the rest to a review queue, report the share automated at 5% errors.

Practice data

The repo generates a dev suite of five data-work families: 1,000 requests and 1,400 questions. Change the seed for unlimited training data.

row_issuechoice · 6What, if anything, is wrong with this order row?
ticket_triage3 questionsWhich team? How urgent? Does a person need to look?

The grading suite is not this file. It has fresh data for these five families plus task families that are not in the repo. An engine that only knows these five won't do well.

The number that matters: automation rate

Sort every decision by confidence. Automate from the top down while errors stay at or below 5%. The share you get through is your automation rate.

Quick start

Needs uv. The kit itself is plain Python 3.11+ with no dependencies.

1. Get the kit and generate the data 
git clone https://github.com/proximata/hackathon-26-think-fast.git && cd hackathon-26-think-fast
uv run python -m thinkfast.suite      # data/dev.jsonl
uv run python -m thinkfast.messy      # data/catalogue_messy.csv + answer key
2. Start an engine on port 8009 (Kev, in its own folder) 
git clone https://github.com/jaredpalmer/kev.git && cd kev
uv sync --extra serve
uv run --extra serve python -m kev.serve --run jaredpalmer/kev-0.8b --port 8009
3. Score it (from the kit folder) 
uv run python -m thinkfast.run_eval --suite data/dev.jsonl --limit 200   # quick check
uv run python -m thinkfast.run_eval --suite data/dev.jsonl               # full dev suite

Prefer your own model? thinkfast/bridge.py turns any local OpenAI-compatible server that returns top_logprobs into an engine. See the README.

Lessons from our dry run

  • Download everything the night before.Kev's install pulled a 6.9 GB environment (6.6 min), and the first start took about 10 more minutes for the weights. Venue Wi-Fi will be shared.
  • Turn thinking off for chat models.Qwen3.5 starts its reply with “Thinking”, so the bridge finds no answer letter and every question becomes a uniform guess. With llama.cpp, start llama-server with --reasoning off.
  • Rehearse with Wi-Fi off.Start your engine from your own README and run the evaluation without a network. Kev restarted offline in 91 s from cached weights.
  • A small GPU is enough to start.Kev-0.8B ran on a 4 GB laptop GPU, using 3.9 GB. Speed depends mostly on hardware and kernels.
  • Calibrate on data you didn't fit on.One temperature fitted on half the dev answers cut Kev's calibration error on the other half from 0.078 to 0.047.

House rules

  • Local only at grading: no hosted model APIs at inference time. Cloud is fine for training.
  • Open weights only; respect every licence, including the terms of any model you generate training data with.
  • Don't train on or look up the hidden suite.

Submit

  • One documented command that starts your engine on port 8009 from a clean checkout. Weights come from a separate setup step.
  • A REPORT.md: your dev-suite numbers from the runner, the model and hardware you measured on, and what you'd do next.

Reading the numbers

Accuracy
Share of questions where your most likely answer is right.
Brier score
How far your probabilities are from the truth. 0 is perfect, lower is better.
Calibration error
Gap between how sure you say you are and how often you're right.
Automation rate
Share of decisions you can take alone with at most 5% errors. The headline number.
p95 latency
95% of requests finish faster than this.
